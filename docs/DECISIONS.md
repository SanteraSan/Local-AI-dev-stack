# Журнал решений

Формат: контекст, решение, последствия. Новые записи добавляются сверху.

## 2026-10-17. qwen2.5-coder не делает нативный вызов инструментов

Контекст: в Open WebUI модель `coder` на обычные вопросы отвечала JSON вида `{"name": "search_knowledge_bases", "arguments": {...}}`. Open WebUI передаёт модели свои встроенные инструменты.

Проверка через шлюз с теми же двумя инструментами:

- `coder` (`qwen2.5-coder-14b-32k`): `tool_calls` пустой, JSON вызова лежит в тексте ответа. Без инструментов в запросе — нормальный текст. Шаблон Ollama инструменты поддерживает, проблема в модели.
- `reasoner` (`qwen3:14b`): настоящие `tool_calls` — `get_current_timestamp` за 2,3 с, `search_knowledge_bases` за 13,7 с.

Решения:

- В Open WebUI для `coder` выключить нативный вызов инструментов; для чата с инструментами использовать `reasoner`. Служебные задачи Open WebUI (заголовки, подсказки) — на `fast`.
- Для агентов, которым нужен нативный tool calling (Roo Code, Cline, OpenCode), `qwen2.5-coder` в роли `coder` не подходит без проверки. Перед фазой 4 — проверка вызова инструментов в бенчмарке; кандидаты: `qwen3:14b`, `qwen3-coder:30b` (MoE, частично на CPU). `qwen2.5-coder` остаётся для чата о коде, правок без инструментов (Aider) и автодополнения.

Последствия: выбор модели `coder` для агентов откладывается до бенчмарка; псевдоним можно будет переназначить в `litellm/config.yaml` без правок в клиентах.

## 2026-10-17. Шлюз LiteLLM: сеть, ключи, логи, версии

Контекст: Ollama слушает только `127.0.0.1` хоста и не имеет авторизации; шлюз должен быть единственной точкой входа для всех клиентов.

Решения:

- LiteLLM и Open WebUI в `network_mode: host`, оба явно привязаны к `127.0.0.1`. В bridge-сети контейнер не видит `127.0.0.1` хоста, а открывать Ollama на `0.0.0.0` нельзя. Open WebUI по умолчанию слушает `0.0.0.0` — поэтому `HOST=127.0.0.1`.
- `keep_alive: -1` для `coder` и `fast` прописан в `litellm/config.yaml`. Без него каждый запрос через шлюз сбрасывал бы прогрев `warmup.sh` на 30 минут из глобального `OLLAMA_KEEP_ALIVE`. Проверено: после запросов обе модели остаются `Forever`.
- Отдельный виртуальный ключ на каждого клиента; ключ devmem ограничен моделью `embed` (проверено: запрос к `coder` — 403).
- `turn_off_message_logging: true`: в журнал расходов пишутся метаданные, но не тексты запросов и ответов. Проверено по `LiteLLM_SpendLogs`.
- Open WebUI считает эмбеддинги для своего RAG через шлюз (`embed`), а не качает отдельную модель с Hugging Face.
- Образы закреплены по digest после первой рабочей сборки: LiteLLM 1.105.1, Open WebUI 0.12.3, PostgreSQL 16.15 + pgvector 0.8.7.

Последствия: облачный fallback подготовлен в конфиге, но выключен до появления ключа. Клиенты подключаются к одному адресу `http://127.0.0.1:4000/v1` со своими ключами.

Замечание по сети: при первой загрузке образов демон Docker один раз пытался подключиться к Docker Hub по IPv6, которого у машины нет, а загрузка через VPN-туннель однажды зависла. Повтор прошёл. Если повторится — проверить VPN, затем рассмотреть `"ipv6": false` / DNS в `/etc/docker/daemon.json`.

## 2026-10-17. TOON — эксперимент, а не формат по умолчанию

Контекст: TOON экономит токены на однородных списках объектов, окно локальной модели 32k.

Решение: сериализация ответов devmem сменная (`json | toon | csv`), по умолчанию компактный JSON. Формат по умолчанию выбирается по бенчмарку: входные токены и точность на `coder`, `reasoner`, `reviewer`.

Последствия: протоколы (MCP, tool calling) и ответы модели остаются JSON; TOON только в тексте ответа инструмента.

## 2026-10-17. Память агентов — MCP-сервер на Postgres + pgvector

Контекст: нужна общая память между сессиями, клиентами (Cursor, Roo, Continue, OpenCode) и моделями.

Решение: отдельный MCP-сервер `devmem` с явными инструментами (решения, итоги шагов, handoff), а не перехват трафика в шлюзе и не файлы в репозиториях. Существующие документы проектов импортируются как записи с `source_path`. Дообучение моделей на файлах репозитория не используется.

Последствия: память — контекст, а не доказательство; агент сверяет записи с кодом. Перезагрузку модели память не решает: история не теряется, клиент присылает её заново.

## 2026-10-17. Порядок загрузки моделей фиксирует warmup.sh

Контекст: `coder` (12 ГБ) и `fast` (2,1 ГБ) помещаются в 16 ГБ с запасом около 1,5 ГБ, только если `coder` загружается первой.

Решение: `ollama/warmup.sh` выгружает все модели и загружает пару в порядке `coder`, затем `fast`, с `keep_alive: -1`.

Последствия: после фаз `reasoner` / `reviewer` прогрев нужно повторять. В будущем — автопрогрев хуком в LiteLLM.

## 2026-10-17. Раскладка моделей под 16 ГБ видеопамяти

Контекст: глобальное окно 16384 раздувало маленькие модели, рабочий стол GNOME использует видеопамять NVIDIA.

Решение: варианты через Modelfile — `coder` с окном 32768, `fast` с окном 4096, эмбеддинги целиком на CPU (`num_gpu 0`). KV-кэш `q8_0` и flash attention включены глобально.

Последствия: `coder` + `fast` занимают 14,8 из 16,3 ГБ. При нехватке памяти сначала освобождать видеопамять (монитор на встроенную графику), и только потом уменьшать окно `coder`.

## 2026-10-17. Отдельный репозиторий для личной AI-инфраструктуры

Контекст: шлюз и память нужны во всех проектах, а не только в TaskFlow.

Решение: `~/dev-ai-stack` — отдельный репозиторий. Клиенты обращаются к псевдонимам по ролям (`coder`, `fast`, `reasoner`, `reviewer`, `vision`, `embed`), а не к реальным именам моделей. Всё слушает только `127.0.0.1`.

Последствия: правки в TaskFlow не ломают инструменты разработки. TaskFlow позже подключается к шлюзу как ещё один провайдер своего `ModelGateway`.
