Что пробовали, что намерили, что сломалось и чем закончилось. Решения с обоснованием — в `DECISIONS.md`, текущее состояние — в `README.md`.

## 2026-10-17: Фаза 1. Ollama под агентский режим на 16 ГБ

Контекст:

- Ollama 0.31.1 работала без единой переменной `OLLAMA_*`: окно, удержание моделей и KV-кэш по умолчанию;
- железо: RTX 5070 Ti 16 ГБ, Ryzen 9 9950X3D, 59 ГБ ОЗУ.

Что изменено:

- systemd-оверрайд: `CONTEXT_LENGTH=16384`, `KEEP_ALIVE=30m`, `MAX_LOADED_MODELS=3`, `NUM_PARALLEL=1`, `FLASH_ATTENTION=1`, `KV_CACHE_TYPE=q8_0`. Копия в `ollama/systemd-override.conf`;
- Modelfile: `qwen2.5-coder-14b-32k` (`num_ctx 32768`), `qwen2.5-coder-3b-4k` (`num_ctx 4096`), `nomic-embed-text-cpu` (`num_gpu 0`);
- `ollama/warmup.sh`: выгрузить всё, загрузить `coder`, затем `fast`, `keep_alive: -1`, ошибки через `curl -fsS` не глотаются.

Проверки:

- опечатка в оверрайде (`"q8_0"1`) дала `OLLAMA_KV_CACHE_TYPE=q8_01`. Поймали через `systemctl show ollama -p Environment`, а не по поведению моделей;
- `coder` с окном 32k: 12 ГБ, `100% GPU`. Размер подтверждает, что KV `q8_0` работает: с f16 кэш занял бы около 3 ГБ сверху;
- `qwen2.5-coder:3b` с глобальным окном 16384 рядом с `coder`: 22% на CPU, эмбеддинги 74% на CPU, видеопамять 15,1 из 16,3 ГБ;
- `fast` с окном 4k, эмбеддинги на CPU: `fast` всё ещё 3–13% на CPU, в зависимости от того, что открыто;
- причина: рабочий стол GNOME на NVIDIA (`Disp.A On`), около 0,6 ГБ на gnome-shell, Chrome, Telegram. Предположение «монитор на встроенной графике» было неверным;
- после выключения аппаратного ускорения Chrome: `coder` 12 ГБ + `fast` 2,1 ГБ, обе `100% GPU`, 14,8 из 16,3 ГБ;
- порядок загрузки важен: `fast` первой — `coder` частично на CPU. Ollama выбирает размещение один раз при загрузке;
- первый вариант прогрева «не сработал»: вторая модель `qwen2.5-coder-1.5b-4k` не была создана, а `curl -s ... > /dev/null` скрыл ошибку. Исправлено на `-fsS`;
- `warmup.sh` вставляли в терминал вместо запуска файлом — `set -euo pipefail` остался в интерактивной сессии. Скрипт запускается только как файл;
- итоговый `warmup.sh`: 9 секунд, обе модели `100% GPU`, `Forever`.

Вывод:

- для 16 ГБ решает не размер модели, а окно, KV-кэш и чужие потребители видеопамяти;
- выгрузка модели не теряет контекст разговора: историю присылает клиент. Теряется время на загрузку и KV-кэш промпта.

Future hardening:

- монитор на встроенную графику Ryzen, вернуть ускорение Chrome, получить запас около 0,6 ГБ;
- автопрогрев через хук LiteLLM вместо ручного `warmup.sh`;
- сравнить `fast` 3B и 1.5B на реальном автодополнении.

## 2026-10-17: Фаза 2. Postgres + pgvector, LiteLLM, Open WebUI

Контекст:

- нужен один OpenAI-совместимый адрес для всех клиентов, Ollama слушает только `127.0.0.1` и без авторизации.

Что изменено:

- `docker-compose.yml`: `pgvector/pgvector:pg16` на `127.0.0.1:5442`, LiteLLM и Open WebUI в `network_mode: host`, привязаны к `127.0.0.1`;
- `postgres/init/01-init.sql`: базы `litellm` и `devmem`, расширение `vector`;
- `litellm/config.yaml`: псевдонимы `coder`, `fast`, `reasoner`, `reviewer`, `vision`, `embed`; `keep_alive: -1` для рабочей пары; `turn_off_message_logging`; облачный fallback закомментирован;
- `litellm/issue-keys.sh`: виртуальные ключи клиентов, повторный запуск не ротирует;
- образы закреплены по digest: LiteLLM 1.105.1, Open WebUI 0.12.3, PostgreSQL 16.15 + pgvector 0.8.7.

Проверки:

- первая загрузка образов: Docker Hub по IPv6 — `network is unreachable`; по IPv4 через `curl -4` отвечал `401`, то есть доступен. Повтор `docker pull` прошёл за 24 с;
- загрузка Open WebUI встала на 6 КиБ/с при активном VPN-туннеле `tun0`. Повтор — 35 МиБ/с, около 3 минут;
- `pkill -f 'docker pull -q'` убил собственную shell-команду: строка была в её тексте. Для поиска процессов — `pgrep` с проверкой;
- Postgres healthy, базы созданы, pgvector 0.8.7;
- LiteLLM поднялся за 25 с, 195 миграций Prisma;
- `/v1/models`: ключ Open WebUI видит все шесть псевдонимов, ключ devmem — только `embed`, без ключа `401`, ключ devmem к `coder` — `403`;
- `coder` 0,58 с, `fast` 0,24 с на однострочный TypeScript; `embed` — 768 измерений;
- после запросов через шлюз `coder` и `fast` остаются `Forever`; без `keep_alive: -1` в конфиге шлюз сбрасывал бы прогрев на 30 минут;
- `LiteLLM_SpendLogs`: 5 записей, поля `messages` и `response` пустые;
- после пересоздания контейнеров (смена ссылки на образ) ключи и данные на месте;
- проверка секретов: ни одно значение из `.env` не встречается в отслеживаемых файлах. Первая версия проверки была ложно-чистой: `git add --dry-run` отдаёт имена в кавычках, и `grep` не открывал файлы.

Вывод:

- шлюз — единственная точка входа, Ollama наружу не открыта;
- облачный fallback не проверен: нет ключа провайдера.

Future hardening:

- выбрать провайдера, включить `coder-cloud`, проверить переключение при остановленной Ollama;
- при повторе сетевых сбоев Docker — `/etc/docker/daemon.json` (IPv6, DNS) или прокси для демона.

## 2026-10-17: Open WebUI и вызов инструментов

Контекст:

- в Open WebUI `coder` на вопросы про Римскую империю отвечал JSON вида `{"name": "search_knowledge_bases", ...}` и `{"name": "get_current_timestamp", ...}`.

Проверки (через шлюз, те же два инструмента, что передаёт Open WebUI):

- `coder` (`qwen2.5-coder-14b-32k`) с инструментами: `tool_calls` пустой, JSON вызова в тексте ответа;
- `coder` без инструментов: нормальный ответ текстом;
- шаблон модели в Ollama блок `Tools` содержит — проблема не в шаблоне;
- `reasoner` (`qwen3:14b`) с инструментами: настоящие `tool_calls`, `get_current_timestamp` 2,3 с, `search_knowledge_bases` 13,7 с;
- после проверки рабочая пара возвращена `warmup.sh`.

Что изменено в Open WebUI (вручную):

- для `coder` вызов функций «По умолчанию» вместо нативного;
- модель внешней задачи — `fast`. Для неё модель должна быть публичной, иначе «Эта модель недоступна в открытом доступе». Все модели из шлюза Open WebUI считает внешними, поле локальной задачи не используется.

Вывод:

- `qwen2.5-coder` не годится в агенты с нативным tool calling (Roo Code, Cline, OpenCode) без отдельной проверки. Это нашлось до фазы 4, а не посреди настройки агентов.

Future hardening:

- проверка tool calling для роли `coder` перед фазой 4: `qwen3:14b`, `qwen3-coder:30b`; доля корректных вызовов, задержка, видеопамять рядом с `fast`.

## 2026-10-17: Фаза 3. MCP-сервер памяти devmem

Контекст:

- нужна общая память между сессиями, клиентами и моделями: решения, уроки, задачи, handoff;
- схема, инструменты, CLI и критерии готовности заданы в плане фазы 3;
- реализацию писал субагент (Grok 4.7) в ветке `phase-3-devmem`, ревью и проверки — отдельно, не по его отчёту. Два раунда замечаний из трёх допустимых.

Что изменено:

- `devmem/migrations/001_init.sql` — схема из плана один в один: `projects`, `tasks`, `entries` с `vector(768)` и `tsvector` на `simple`, HNSW, GIN. Применённые миграции учитываются в `schema_migrations`;
- `devmem/devmem/server.py` — FastMCP 1.30, Streamable HTTP на `127.0.0.1:8765/mcp`, bearer через `hmac.compare_digest`, защита от DNS rebinding, `--stdio` запасной; 8 инструментов и ресурс брифа;
- `search.py` — полнотекст и вектор, RRF с `k=60`; `secrets_filter.py` — отказ, а не вырезка; `serialize.py` — `json | toon | csv`, обрезка `content`, без служебных полей;
- `cli.py` — `migrate`, `project add`, `import`, `search`, `export`, `reindex`, `serve`;
- `devmem/systemd/devmem.service` — юнит в репозитории, не установлен;
- 81 тест: unit без сети, HTTP-авторизация, интеграционные на `devmem_test`, порядок «проверка → эмбеддинг → транзакция».

Проверки:

- `uv run pytest -q`: `81 passed`, пропусков нет;
- `ss -ltn`: только `127.0.0.1:8765`; без токена и с неверным токеном — `401`, чужой `Host` — `421`;
- MCP Inspector в режиме `--cli`: 8 инструментов и шаблон `devmem://project/{slug}/brief`; без заголовка — отказ;
- ревью, раунд 1. Живой проверкой нашли: `memory_save` с `postgresql://devai:<пароль>@...` сохранился. В `.env` строки ровно такой формы. Добавлен паттерн `url_credentials`, расширены присваивания (`api_key=`, `"password": "..."`, `PG_PASSWORD=`);
- раунд 1, по коду: эмбеддинг (таймаут 60 с) шёл внутри транзакции, а в `supersede` — под `FOR UPDATE`. Бриф резался по символам, JSON внутри ломался, 20 задач могли вытеснить handoff. `source_path` хранился абсолютным путём `/home/...`. Всё исправлено: секреты проверяются до шлюза, handoff в брифе первым, секции урезаются по элементам, путь относительно корня проекта;
- раунд 2: повторный импорт пересчитывал векторы всех секций, запись в незарегистрированный проект сначала ходила в шлюз, поиск держал соединение во время HTTP-вызова. Исправлено, покрыто тестами со счётчиком вызовов эмбеддинга;
- импорт `LESSONS_LEARNED.md` TaskFlow (4778 строк) в рабочую базу: 146 секций за 32 с, у всех есть вектор, повторный импорт — `inserted=0 skipped=146`, `source_path = research/LESSONS_LEARNED.md`;
- поиск по точному заголовку («PostgreSQL слой для RAG logs») — нужная секция первой. По смысловому вопросу («как модель отвечает, когда в документах нет ответа») наверху служебные секции журнала: «Как вести журнал» и шаблон `YYYY-MM-DD`;
- первый импорт ушёл в `devmem_test`: в shell осталась `DEVMEM_DATABASE_URL` от смоук-теста, переменная окружения перекрывает `.env`. Поймали по строке `on database devmem_test` у `migrate`, тестовую базу очистили;
- `pkill -f` и `pgrep -f` по шаблону, который есть в тексте собственной команды, снова убили shell. Сервер останавливаем по PID из `ss -ltnp`;
- значений из `.env` нет ни в диффе, ни в истории.

Вывод:

- память работает от записи до брифа, рабочая база наполнена уроками TaskFlow;
- самые ценные находки ревью — живые проверки, а не чтение кода: строку подключения с паролем тесты субагента не ловили, потому что сами её не проверяли;
- качество смыслового поиска на реальном корпусе среднее: без реранкера и порога близости служебные секции документа конкурируют с содержательными.

Future hardening:

- исключать при импорте служебные секции (шаблоны, «как вести журнал») или помечать их отдельным `kind`;
- реранкер и порог близости для вектора: сейчас поиск всегда возвращает `k` записей;
- `memory_supersede` с несуществующим `entry_id` считает эмбеддинг до проверки;
- установить systemd-юнит от пользователя и проверить автозапуск после перезагрузки;
- сценарий «решение в Cursor → бриф в Roo на `coder`» — в фазе 4, вместе с заголовком `X-Devmem-Client`;
- по желанию сменить `PG_PASSWORD`: на первом прогоне pytest строка подключения к тестовой базе попала в локальный лог субагента. В репозиторий она не попала.

## 2026-10-17: Проверка tool calling перед выбором модели агента

Контекст:

- перед фазой 4 нужно было выбрать модель для агентов с нативным tool calling. В Open WebUI `qwen2.5-coder` писал JSON вызова текстом.

Что изменено:

- прогон не менял алиас `coder`. Временный `agent-candidate` на `qwen3-14b-32k` в закоммиченный `litellm/config.yaml` не входил. Итог — `bench/results/2026-10-17-tool-calling-summary.md`.

Проверки:

- шлюз `http://127.0.0.1:4000/v1/chat/completions`, 15 кейсов, temperature 0. Инструменты не выполнялись: после `tool_calls` в историю подставлялся синтетический `role: tool`;
- промпты пошаговые и короткие. Настоящий промпт Roo Code намного больше. Режим thinking у `qwen3` не переключался;
- `coder` (`qwen2.5-coder-14b-32k`): правильный инструмент 3/15, где инструмент нужен 0/12, валидные аргументы 0/12, совпадение аргументов 0/12, ложные срабатывания 0/3, средняя задержка 0,76 с. На всех 12 нужных кейсах JSON с верным именем и аргументами был в тексте при пустых `tool_calls`. Совместно с `fast`: не обе 100% GPU (`fast` 3%/97% CPU/GPU, nvidia 14849/16303 МиБ);
- `reasoner` (`qwen3:14b`, окно 16384): 15/15, 12/12, аргументы 12/12, ложные 0/3, 4,41 с, вместе с `fast` обе 100% GPU, 10 ГБ;
- `qwen3-14b-32k`: 15/15, 12/12, аргументы совпали 12/12, ложные 0/3, 4,10 с, 11 ГБ, 100% GPU, вместе с `fast` обе 100% GPU, nvidia 14589/16303 МиБ;
- `warmup.sh` после прогона трижды оставлял `fast` на 3%/97% CPU/GPU при `coder` 100% GPU. Повторная загрузка `fast` с `num_gpu: 99` вернула обе на 100% GPU.

Вывод:

- для нативных агентов берётся `qwen3-14b-32k`, не `qwen2.5-coder`. Окно 32k у `qwen3` влезает рядом с `fast` (14,6 ГБ). Это лабораторный прогон: короткие пошаговые промпты и синтетические ответы инструментов, не нагрузка Roo Code.

Future hardening:

- прогнать тот же набор на реальном системном промпте Roo Code;
- сравнить качество правок кода `qwen3-14b-32k` и `qwen2.5-coder`, прежде чем сводить роли в одну резидентную модель;
- проверить thinking mode `qwen3`, если агент начнёт тратить окно на рассуждение.

## 2026-10-17: Псевдоним agent и устойчивый прогрев

Контекст:

- проверка tool calling выбрала `qwen3-14b-32k` для агентов, а `coder` остаётся на `qwen2.5-coder` для работы без инструментов. `warmup.sh` иногда оставлял `fast` частично на CPU: Ollama фиксирует размещение при загрузке, а видео и браузер занимают видеопамять.

Что изменено:

- `litellm/config.yaml`: псевдоним `agent` на `ollama_chat/qwen3-14b-32k`, `keep_alive: -1`. Остальные алиасы не менялись;
- `litellm/issue-keys.sh`: `agent` в полном списке новых ключей, devmem по-прежнему только `embed`;
- `litellm/sync-key-models.sh`: обновляет allowlist уже выпущенных ключей через `/key/update`, без ротации. Печатает имя переменной и статус;
- `ollama/warmup.sh`: `warmup.sh [coder|agent]`, по умолчанию `coder`. Большая модель первой, затем `fast`. Если `fast` не на 100% GPU — выгрузка и одна повторная загрузка. Если после этого большая модель или `fast` не на 100% GPU — предупреждение с занятой видеопамятью и крупными потребителями из `nvidia-smi`, код 2. `--force-gpu` грузит `fast` с `num_gpu: 99` и может упасть, если памяти правда не хватает.

Проверки:

- `bash -n` для `issue-keys.sh`, `sync-key-models.sh`, `warmup.sh` — без ошибок. `shellcheck` в системе нет;
- `docker compose config -q` — код 0. `docker compose restart litellm`, затем `http://127.0.0.1:4000/health/liveliness` — 200 (два первых опроса не подключились, третий — 200);
- `sync-key-models.sh`: первый запуск обновил пять клиентских ключей, `LITELLM_DEVMEM_KEY` уже совпадал; второй запуск — все `already matches`. Значения ключей не печатались, `.env` не менялся;
- ключ Roo: `GET /v1/models` 200, в списке есть `agent` (и `coder`, `fast`, `reasoner`, `reviewer`, `vision`, `embed`). Ключ devmem: 200, только `embed`;
- один запрос `agent` с инструментом `read_file` («Прочитай файл src/app.py»): HTTP 200, `tool_calls` есть, один вызов `read_file`, `finish_reason=tool_calls`, 2,34 с. Запрос шёл после прогрева профиля `agent`;
- `./ollama/warmup.sh agent` — код 0. `qwen3-14b-32k` 11 ГБ 100% GPU Forever, `qwen2.5-coder-3b-4k` 2,1 ГБ 100% GPU Forever;
- `./ollama/warmup.sh coder` — код 0. `qwen2.5-coder-14b-32k` 12 ГБ 100% GPU Forever, `fast` 2,1 ГБ 100% GPU Forever. Машина оставлена в этом профиле;
- `./ollama/warmup.sh --force-gpu coder` — код 0, обе модели снова 100% GPU. Неизвестный аргумент — код 1, модели не выгружаются. Код 2 в этом прогоне не случился: видеопамяти хватило без повторной загрузки `fast`.

Вывод:

- `agent` доступен существующим клиентским ключам и отдаёт нативный `tool_calls`. Прогрев умеет два профиля и сообщает о неполном размещении кодом 2, но сегодня этот путь не проверялся вживую.

Future hardening:

- поймать код 2 при реальном видео на NVIDIA и убедиться, что предупреждение называет этот процесс;
- автопрогрев нужного профиля из клиента, а не ручной `warmup.sh`;
- сравнить качество правок `qwen3-14b-32k` и `qwen2.5-coder` до решения оставить одну резидентную модель.
